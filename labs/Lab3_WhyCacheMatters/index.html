    1. Understanding Memory Hierarchy and Cache

    The Memory Hierarchy

    Modern computer systems use a memory hierarchy to balance speed, capacity, and cost. Each level has typical capacities and access times:

    CPU Registers    ~1 cycle     ~1 KB       Fastest
L1 Cache        ~3 cycles    ~32 KB      
L2 Cache        ~10 cycles   ~256 KB     
L3 Cache        ~40 cycles   ~8 MB       
Main Memory     ~200 cycles  ~8 GB       
SSD/HDD         ~10^6 cycles ~1 TB       Slowest
    • Registers: Fastest, smallest storage for immediate computations.
    • Caches (L1, L2, L3): Store frequently accessed data; typical sizes like 32KB (L1) or 256KB (L2) vary by CPU.
    • Main Memory (RAM): Holds program data and instructions.
    • Storage (SSD/HDD): Persistent, slowest storage.

    Cache Principles

    Caches reduce memory access time by keeping recently used data near the CPU:

    • Cache Line: The smallest unit of data transferred between cache and main memory, typically 64 bytes. Fetching one byte loads the entire line, leveraging spatial locality.
    • Cache Hit: Data is found in the cache (e.g., 3 cycles for L1).
    • Cache Miss: Data must be fetched from slower memory (e.g., 200 cycles from RAM), causing delays.
    • Cache Eviction: When the cache is full, older data is replaced using policies like Least Recently Used (LRU).

    Why Cache Matters: Understanding Cache Locality

    Cache performance hinges on locality of reference, which comes in two flavors:

    • Spatial Locality: If a program accesses a memory location, it’s likely to access nearby locations soon. CPUs load data in cache lines (e.g., 64 bytes), so accessing consecutive memory locations (like array elements) maximizes cache line usage, reducing misses.
    • Temporal Locality: If a program accesses a memory location, it’s likely to access it again soon. Reusing data while it’s still in the cache avoids fetching it from slower memory.

    Let’s explore these concepts with two simple examples before a performance demonstration.

    Example 1: Spatial Locality with Array Traversal

    Consider a program that processes a small array of integers, comparing sequential (cache-friendly) versus non-sequential (cache-unfriendly) access.

    #include <iostream>
#include <vector>

const int SIZE = 16; // Small for illustration

// Sequential access (good spatial locality)
long long sum_sequential(const std::vector<int>& arr) {
    long long sum = 0;
    for (int i = 0; i < SIZE; i++) {
        sum += arr[i]; // Consecutive accesses
    }
    return sum;
}

// Non-sequential access (poor spatial locality)
long long sum_nonsequential(const std::vector<int>& arr) {
    long long sum = 0;
    // Access every 4th element, cycling through
    for (int step = 0; step < 4; step++) {
        for (int i = step; i < SIZE; i += 4) {
            sum += arr[i]; // Non-consecutive accesses
        }
    }
    return sum;
}

int main() {
    std::vector<int> arr(SIZE, 1); // Array of 1s
    std::cout << "Sequential sum: " << sum_sequential(arr) << "\n";
    std::cout << "Non-sequential sum: " << sum_nonsequential(arr) << "\n";
    return 0;
}

    How It Works: - Sequential Access: Iterates through arr[0], arr[1], arr[2], ..., loading one cache line (e.g., 64 bytes, or 16 integers) that covers multiple elements, minimizing misses. - Non-Sequential Access: Accesses arr[0], arr[4], arr[8], arr[12], then arr[1], arr[5], ..., jumping 16 bytes each time, potentially requiring multiple cache lines. - Cache Perspective: Sequential access uses one cache line efficiently, while non-sequential access wastes cache space.

    Output: 

    Sequential sum: 16
Non-sequential sum: 16
    Sequential access is faster due to better cache line utilization.

    Why Spatial Locality Matters: Accessing contiguous memory leverages the cache line’s full capacity, reducing slow memory fetches.

    Example 2: Temporal Locality with Repeated Data Access

    To demonstrate temporal locality, we’ll compare two approaches to computing a weighted sum of an array. The first reuses a small subset of data multiple times (good temporal locality), while the second accesses a larger dataset each time (poor temporal locality).

    #include <iostream>
#include <vector>

const int SIZE = 1000;
const int SMALL_SIZE = 10;

// Good temporal locality: reuse a small dataset
long long sum_weighted_reuse(const std::vector<int>& arr) {
    long long sum = 0;
    std::vector<int> weights(SMALL_SIZE, 2); // Small array, fits in cache
    for (int i = 0; i < SIZE; i++) {
        // Reuse weights repeatedly
        for (int j = 0; j < SMALL_SIZE; j++) {
            sum += arr[i] * weights[j];
        }
    }
    return sum;
}

// Poor temporal locality: access large dataset each time
long long sum_weighted_large(const std::vector<int>& arr) {
    long long sum = 0;
    std::vector<int> weights(SIZE, 2); // Large array, exceeds cache
    for (int i = 0; i < SIZE; i++) {
        // Access different weights each time
        for (int j = 0; j < SIZE; j++) {
            sum += arr[i] * weights[j];
        }
    }
    return sum;
}

int main() {
    std::vector<int> arr(SIZE, 1); // Array of 1s
    std::cout << "Reuse sum: " << sum_weighted_reuse(arr) << "\n";
    std::cout << "Large sum: " << sum_weighted_large(arr) << "\n";
    return 0;
}

    How It Works: - Reuse (Good Temporal Locality): Uses a small weights array (10 elements, ~40 bytes), which easily fits in L1 cache (e.g., 32KB). Each weight is reused 1000 times across iterations of i, keeping the data in cache and avoiding refetches from RAM. - Large (Poor Temporal Locality): Uses a large weights array (1000 elements, ~4KB), which may not fit entirely in L1 cache. Each iteration accesses different elements, potentially causing cache misses if the data is evicted. - Cache Perspective: The small weights array stays in cache, ensuring fast access (hits) due to repeated use. The large weights array may require frequent refetches from RAM, increasing latency.

    Output: 

    Reuse sum: 20000     // 1000 * 10 * 2
Large sum: 2000000   // 1000 * 1000 * 2
    While the sums differ due to different numbers of operations, the key is that sum_weighted_reuse runs faster per operation because it reuses cached data.

    Why Temporal Locality Matters: Repeatedly accessing the same data while it’s in the cache avoids costly memory fetches, improving performance.

    Performance Demonstration: Sequential vs. Strided Access

    Now, let’s scale up to a larger array to measure the performance impact of cache locality, focusing on spatial locality.

    #include <iostream>
#include <chrono>
#include <vector>

const int ARRAY_SIZE = 64 * 1024 * 1024; // 64MB array (larger than cache)

// Cache-friendly: sequential access
long long sum_sequential(const std::vector<int>& arr) {
    long long sum = 0;
    for (int i = 0; i < ARRAY_SIZE; i++) {
        sum += arr[i];
    }
    return sum;
}

// Cache-unfriendly: strided access
long long sum_strided(const std::vector<int>& arr) {
    long long sum = 0;
    int stride = 1024;
    for (int iteration = 0; iteration < stride; iteration++) {
        for (int i = iteration; i < ARRAY_SIZE; i += stride) {
            sum += arr[i];
        }
    }
    return sum;
}

int main() {
    std::cout << "=== Cache Locality Demonstration ===\n";

    std::vector<int> data(ARRAY_SIZE);
    for (int i = 0; i < ARRAY_SIZE; i++) {
        data[i] = i % 1000;
    }

    auto start = std::chrono::high_resolution_clock::now();
    long long result1 = sum_sequential(data);
    auto end = std::chrono::high_resolution_clock::now();
    auto sequential_time = std::chrono::duration_cast<std::chrono::milliseconds>(end - start);

    start = std::chrono::high_resolution_clock::now();
    long long result2 = sum_strided(data);
    end = std::chrono::high_resolution_clock::now();
    auto strided_time = std::chrono::duration_cast<std::chrono::milliseconds>(end - start);

    std::cout << "Sequential sum: " << result1 << " (Time: " << sequential_time.count() << " ms)\n";
    std::cout << "Strided sum: " << result2 << " (Time: " << strided_time.count() << " ms)\n";
    std::cout << "Performance ratio: " << (double)strided_time.count() / sequential_time.count() << "x slower\n";

    return 0;
}

    Sample Output (varies by system): 

    === Cache Locality Demonstration ===
Sequential sum: 33553408000 (Time: 78 ms)
Strided sum: 33553408000 (Time: 156 ms)
Performance ratio: 2x slower

    Analysis: - Sequential Access: Iterates contiguously, loading cache lines (e.g., 64 bytes, or 16 integers) that are fully utilized, minimizing misses. - Strided Access: Jumps by 1024 elements (4096 bytes), likely requiring a new cache line per access, increasing misses. - Connection to Pthreads: In your Pthreads labs, you’ve split arrays across threads. Poor locality in each thread’s access pattern (e.g., strided access) would amplify cache misses in parallel programs.

    Experiment: Vary the stride (e.g., 16, 256, 2048) to see how it affects performance. Smaller strides reduce the performance gap by staying within cache lines.
